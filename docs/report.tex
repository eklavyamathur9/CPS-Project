% 1. GENERAL APPLICATION
% ============================================================
\section{General Application}

This project implements a \emph{software-based simulation} of an acoustic
side-channel attack on a mechanical keyboard. In the proposed approach, each
keyboard key is associated with a custom frequency signature. When a key is
pressed within the software model, its corresponding frequency is generated and
represented as a synthetic signal.

The software then analyzes the frequency pattern and maps it back to the
corresponding key. The fundamental pipeline is:

\begin{center}
\textbf{Key Press} $\rightarrow$ \textbf{Custom Frequency} $\rightarrow$
\textbf{Frequency Analysis} $\rightarrow$ \textbf{Key Identification}
$\rightarrow$ \textbf{Keystroke Reconstruction}
\end{center}

This approach demonstrates the acoustic side-channel concept entirely through
software, without requiring a microphone or additional sensing hardware. It is
a \emph{prototype/simulation} of the side-channel reconstruction concept and
the corresponding Cyber-Physical Systems (CPS) verification requirements.

% ============================================================
% 2. OBJECTIVE
% ============================================================
\section{Objective}

The main objective is to develop a software system capable of identifying and
reconstructing keystrokes using predefined frequency signatures. The system
aims to:

\begin{enumerate}
    \item Assign a distinct frequency/signature to each key.
    \item Generate or process the corresponding frequency when a key is activated.
    \item Analyze the frequency signal.
    \item Match the detected frequency with the corresponding key.
    \item Reconstruct the sequence of detected keystrokes.
    \item Measure the execution time and accuracy of the system.
    \item Verify that the system maintains predefined safety and correctness
          properties.
\end{enumerate}

% ============================================================
% 4. CPS APPLICATION: REAL-TIME REQUIREMENTS (WCET)
% ============================================================
\section{Cyber-Physical Systems Application: WCET}

The software operates as a real-time task. The processing pipeline is:

\[
\text{Input Key} \rightarrow \text{Frequency Generation} \rightarrow
\text{Frequency Analysis} \rightarrow \text{Frequency Matching} \rightarrow
\text{Key Output}
\]

The total execution time can be expressed as:

\[
T_{\text{total}} = T_{\text{input}} + T_{\text{frequency}}
+ T_{\text{analysis}} + T_{\text{matching}} + T_{\text{output}}
\]

We measure three timing quantities:

\begin{itemize}
    \item \textbf{Average execution time}: the mean processing time per key.
    \item \textbf{Maximum execution time}: the observed worst case in a single
          run.
    \item \textbf{WCET (median)}: the median of the per-key worst-case times
          across multiple trials.
    \item \textbf{WCET (P95)}: the $95$th percentile of the per-key
          worst-case times across multiple trials.
\end{itemize}

Because a single-trial timing measurement can be dominated by scheduler or
measurement noise, the implementation runs the reconstruction over a number of
trials (\texttt{WCET\_TRIALS} $= 20$) and reports \emph{robust} statistics: the
\textbf{median} (typical worst case) and the \textbf{P95} (a conservative worst
case) of the observed reconstruction times. The P95 value is computed with a
nearest-rank percentile,
\[
\text{P95 index} = \min(\lceil n \cdot 0.95 \rceil - 1,\; n - 1),
\]
which reports an exact $95$th percentile for any trial count.

The real-time requirement is:

\[
T_{\text{WCET}} < T_{\text{deadline}}
\]

This ensures the software can process a key/frequency before the next required
input is processed.

\subsection{Why this matters}

If the processing time becomes too large, the system may:
\begin{itemize}
    \item Miss a key event.
    \item Process keys in the wrong order.
    \item Produce an incorrect reconstruction.
    \item Lose synchronization with the input sequence.
\end{itemize}

In our implementation, the deadline is set to $50$ ms. The system always
completes processing well within this bound, and the reported worst case
(median and P95) remains below the deadline, satisfying the real-time
requirement.

% ============================================================
% 5. INVARIANTS
% ============================================================
\section{Finding and Proving Invariants}

An \emph{invariant} is a property that must remain true throughout program
execution. Our system maintains the following invariants.

\subsection{Invariant 1: Valid Frequency}

Every generated/detected frequency must belong to the predefined frequency
set:

\[
\Freq \in \{F_1, F_2, F_3, \ldots, F_n\}
\]

\subsection{Invariant 2: Valid Key Mapping}

Every valid frequency must map to a valid key:

\[
F_i \rightarrow K_i
\]

\subsection{Invariant 3: One-to-One Mapping}

Each frequency must correspond to exactly one predefined key. This prevents
ambiguity between keys:

\[
F_i \neq F_j \quad \text{for } i \neq j
\]

\subsection{Invariant 4: Sequence Preservation}

If the input sequence is $K_1, K_2, K_3, \ldots, K_n$, then the reconstructed
sequence must preserve the same ordering (assuming all inputs are successfully
processed).

% ============================================================
% 6. CONVERGENCE, LIVENESS AND TERMINATION
% ============================================================
\section{Convergence, Liveness and Termination}

\subsection{Convergence}

The system uses a frequency-matching threshold. The detected frequency should
converge toward the predefined frequency/signature of the selected key:

\[
|F_{\text{detected}} - F_{\text{key}}| < \epsilon
\]

where $\epsilon$ is the permitted frequency error (the tolerance). When this
condition is satisfied, the software identifies the corresponding key.

\subsection{Liveness}

The system must continuously be able to process new key/frequency events:

\[
\text{Input} \rightarrow \text{Analyze} \rightarrow \text{Identify}
\rightarrow \text{Output} \rightarrow \text{Wait for next input}
\]

The system does not get permanently stuck during frequency analysis or key
identification. This is verified programmatically by the \texttt{liveness\_test()}
function.

\subsection{Termination}

When the user stops the application:
\[
\text{Stop} \rightarrow \text{Finish current operation} \rightarrow
\text{Save results} \rightarrow \text{Release resources} \rightarrow \text{Exit}
\]

A finite input sequence always terminates. This is verified by the
\texttt{termination\_test()} function, which checks that a fixed sequence
completes within a bounded time.

% ============================================================
% 7. RANKING FUNCTION
% ============================================================
\section{Ranking Function}

For this project, we define an error-based ranking function based on the
difference between the detected frequency and the expected frequency:

\[
V = |F_{\text{detected}} - F_{\text{expected}}|
\]

A successful frequency-matching process minimizes this error. The desired
condition is:

\[
V \rightarrow 0
\]

or, with a tolerance:

\[
V < \epsilon
\]

The frequency-error function $V$ is used as a \emph{ranking measure} for the
identification process. As the detected frequency becomes closer to the
predefined frequency of a key, the error decreases and the system approaches
the correct key classification.

The key with the smallest $V$ value (i.e., the minimum error) is selected as
the matching key, provided $V \leq \epsilon$ (the tolerance).

% ============================================================
% 8. SAFETY PROPERTIES
% ============================================================
\section{System Will Never Do Something Catastrophic}

For our software CPS, we define the \emph{catastrophic/failure conditions} as:

\begin{itemize}
    \item An invalid frequency being accepted as a valid key.
    \item Two keys having the same frequency.
    \item An incorrect key mapping.
    \item Processing exceeding the deadline.
    \item Loss of input sequence.
    \item The application entering an invalid state.
\end{itemize}

The safety conditions are therefore:

\[
\Freq \in \Freq_{\text{valid}}
\]
\[
F_i \neq F_j \quad (i \neq j)
\]
\[
T_{\text{WCET}} < T_{\text{deadline}}
\]
\[
\text{Output} \in K_{\text{valid}} \cup \{\text{Unknown}\}
\]

The \Key{Unknown} state is important: the software must not force an incorrect
key when the frequency does not sufficiently match any predefined signature.

\subsection{Spectrogram}

The spectrogram visualization (Figure~\ref{fig:spec}) shows the frequency (Hz)

\begin{figure}[H]
    \centering
    \includegraphics[width=0.85\textwidth]{waveform_spectrogram.png}
    \caption{Simulated frequency spectrogram of the key sequence
             \Key{HELLO WORLD}. Each cyan dashed line marks the expected
             frequency of a key.}
    \label{fig:spec}
\end{figure}

\subsection{Interactive Keypad and Live Updates}

In addition to batch analysis, the application provides an on-screen
\textbf{keypad} (A--Z + 0--9 + SPACE + Clear). Clicking a keypad button
simulates a single key press and \emph{incrementally updates} both plots
live:

\begin{enumerate}
    \item The key is appended to the accumulated sequence.
    \item The frequency pipeline (\texttt{generate\_frequency} $\rightarrow$
          \texttt{process\_frequency}) is executed for that key.
    \item The spectrogram and the sine-wave plots are refreshed in place,
          growing with each added key.
    \item The status bar shows the latest per-key frequency, detected key,
          error, and processing time.
\end{enumerate}

This live interaction demonstrates the real-time nature of the system: every
key event is processed immediately, within the deadline, and the
reconstruction evolves continuously. The \Key{Clear} button resets the
sequence and the plots. The incremental update logic is factored into pure
functions (\texttt{update\_spectrogram}, \texttt{update\_sine\_plot}) so it is
independently unit-testable.

\subsection{Statistical Confidence}

For every detected key, the system reports a per-key \emph{confidence} score in
the range $0.0$--$1.0$ that expresses how close the detected frequency is to the
predefined signature of the matched key:

\[
C = 1 - \frac{|F_{\text{detected}} - F_{\text{expected}}|}{\text{TOLERANCE}},
\]

clamped to $[0, 1]$. An error of $0$ Hz gives $C = 1.0$ (a perfect match), and
an error at the tolerance limit gives $C = 0.0$. The \Key{UNKNOWN} state always
reports $C = 0.0$. This provides a transparent, per-key measure of match
quality alongside the raw error $V$.

\subsection{Report Export and Copy}

The complete analysis (invariant check, per-key frequency mapping with
confidence, reconstructed sequence, WCET/deadline result, ranking, liveness and
termination) is assembled by a single \texttt{format\_report()} function and
displayed in the output panel. From the \texttt{File} menu, the user can:

\begin{itemize}
    \item \textbf{Export report}: save the analysis to a plain-text file,
          optionally including the sine and spectrogram plots as PNG images
          alongside it.
    \item \textbf{Copy results}: copy the current analysis output to the
          clipboard for pasting into another application.
\end{itemize}

Because both the on-screen output and the exported report are generated by the
same \texttt{format\_report()} function, the two are always identical.

\section{Conclusion}

This project successfully demonstrates a software-based simulation of an
acoustic side-channel attack on a mechanical keyboard. By assigning unique
frequency signatures to each key and implementing a matching/ranking mechanism,
the system reconstructs keystroke sequences from the simulated frequency
signals.

The implementation satisfies all the CPS verification requirements:
\begin{itemize}
    \item \textbf{WCET} is measured across multiple trials and its median and
          P95 are shown to satisfy the real-time deadline.
    \item \textbf{Invariants} (positive, unique, and valid frequencies;
          sequence preservation) are defined and verified for all 37 keys.
    \item \textbf{Liveness} and \textbf{termination} are demonstrated
          programmatically.
    \item A \textbf{ranking function} $V = |F_{\text{detected}} - F_{\text{expected}}|$
          quantifies match quality.
    \item A per-key \textbf{confidence} $C$ expresses match quality in $[0,1]$.
    \item \textbf{Safety} is ensured through the \Key{UNKNOWN} state, which
          prevents incorrect key assignment.
\end{itemize}

The project provides a complete, verifiable CPS model and a graphical
interface suitable for demonstration in a project presentation. The on-screen
keypad (A--Z + 0--9 + SPACE) lets a presenter type a sequence live and watch
the sine and spectrogram plots grow with each key press, while the status bar
reports the per-key frequency, error, and execution time in real time. The
full analysis can be exported as a text report (optionally with the waveform
plots) or copied to the clipboard for sharing.
